## 四条任务的工程基线

| 任务 | 本轮结果 | 已观察的使用限制或待研究问题 |
| --- | --- | --- |
| 建官网 | 模板 → 修改首屏标题 → 保存刷新 → 桌面/手机预览通过 | 固定画布在手机预览中等比缩小，文字明显变小；需检查用户能否找到并理解“启用自适应布局”。本轮没有把默认缩放记为手机可读性通过。 |

## 真实用户测试准备

至少安排一组首次使用者和一组熟练用户；首轮建议各 3 人用于定性发现问题，不以小样本推断总体成功率。用 N1/N2、E1/E2 等代号记录，不保存账号、密钥或个人资料。

主持人在仓库根目录执行：

```sh
npm run build
node scripts/serve-m0-user-study.mjs
```

[测试服务](../scripts/serve-m0-user-study.mjs) 输出工作台 URL、GET 列表/详情、POST 和 PUT 地址；只监听 `127.0.0.1`，账号关闭，示例写入只修改进程内存。它不自动加载 `.env`，不使用项目 `data/`。每位参与者重启服务并使用新的无痕/临时浏览器配置，退出用 Ctrl+C；接口停止后，依赖它的导出页面不能继续查询数据。

向参与者提供工作台 URL、任务卡与示例接口说明；不先展示操作指南、成功路径或控件位置。主持人可以解释测试目标，但每次操作提示要记为一次帮助。卡住或出错时保留结果，不指导后再记成“独立成功”。AI 和云端发布不属于这次四条任务，避免额外账号条件改变基线。

示例接口字段为 `id`、`title`、`category`、`amount`。初始“网站”合计 200，“工具”合计 260；GET 支持 `page/pageSize`。POST/PUT 的 JSON 为 `{"title":"新项目","category":"网站","amount":150}`，`amount` 必须为数字。测试前主持人确认 GET 返回 4 条记录即可，避免预先新增记录影响汇总。

## 给参与者的任务卡

| ID | 可直接读给参与者的目标 | 主持人检查的成功条件 |
| --- | --- | --- |
| T1 建官网 | “为一个名为青禾的小工作室做一个主页，替换主标题和介绍，预览效果，并找到以后继续修改的方法。” | 不读文档完成有效预览；刷新后内容保留。记录从打开工作台到有效预览的时间；**5 分钟**是待验证目标。 |
| T2 接 API | “用提供的接口展示项目名称、分类和金额，点击一条项目能看到对应详情。说明数据来自哪里。” | 实际 GET 数据、列表映射、`/projects/:id` 详情匹配；参与者能区分示例数据与接口数据。 |
| T3 做图表 | “按分类比较项目金额，切换另一种图形，查看对应明细，保存一份可在浏览器打开的结果。” | 网站 200、工具 260；切换类型保留映射；同源表格/筛选可用；HTML 下载后在服务运行期间能读取数据。 |
| T4 提交表单 | “给项目表增加一条‘活动页面／网站／150’，再把金额改为 180。提交前说明将发生什么。” | 未确认前没有写入；确认后 POST/PUT 正确；错误输入能修正；能解释保存草稿、外部写入及恢复输入的区别。 |

T2–T4 可在 T1 的作品上继续。若前一步失败，主持人帮助恢复到可继续状态，必须记录预置内容并单独统计后续任务；不能把帮助后完成计为全流程独立成功。T2–T4 首轮记录实际时间和停止原因，不临时编造通过时限。

熟练用户额外检查：搜索高级属性后继续编辑；收起设置组并刷新；撤销一次内容修改；找到固定画布和响应式的区别；确认工作台外观与页面主题互不混淆。两组均回答“数据来自哪里、改动影响哪里、当前是否已经公开”。
